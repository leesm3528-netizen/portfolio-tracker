## 1. 작업 수행 규칙

### 1.1 작업 고르기

1. HANDOFF.md 의 "## 다음 할 작업" 에 적힌 첫 번째 작업 ID 를 고른다.
2. 10절 표에서 그 작업의 선행 작업이 모두 "완료" 인지 확인한다. 하나라도 "대기" 면 선행 작업부터 한다. 3.1 에 상태가 "미해결" 인 M 항목이 있으면 그 영향 작업은 시작하지 않는다.
3. 한 번에 작업 하나만 한다. 두 작업의 변경을 한 커밋에 섞지 않는다.
4. 이 문서에 없는 작업이 필요하면 코드를 쓰기 전에 이 문서에 작업 항목을 먼저 추가하고 사용자에게 알린다. 작업 ID 는 같은 단계의 다음 번호를 쓰고, 이미 쓴 번호는 다시 쓰지 않는다.

### 1.2 작업 전 읽을 문서

읽는 문서와 순서는 AGENTS.md 2절이 원본이다. 이 문서에서는 다시 정하지 않는다.

2단계(T2) 완료 전에는 skills/ 가 없다. 그동안은 이 문서 2절의 검증 방법을 직접 따른다.

### 1.3 완료 처리 절차

작업마다 아래 순서를 지킨다. 앞 단계가 통과하지 않으면 다음 단계로 가지 않는다.

1. 완료 기준 확인: 작업 항목의 "- [ ]" 목록을 하나씩 확인한다. 하나라도 만족하지 않으면 작업을 계속한다.
2. 검증: 작업 항목의 "검증 방법" 을 실행한다(2절). 실패하면 원인을 고치고 다시 실행한다.
3. HANDOFF 갱신: handoff-update 스킬로 HANDOFF.md 를 갱신하고, 이 문서 10절 표의 상태를 "완료" 로 바꾼다.
4. 커밋: AGENTS.md 8절 규칙으로 커밋한다. 커밋에는 그 작업의 변경, HANDOFF.md, 이 문서의 상태 변경만 넣는다.

작업을 끝내지 못하고 멈춰야 하면 커밋하지 않은 변경을 HANDOFF.md 의 "## 알려진 문제" 와 "## 다음 작업자에게 주의사항" 에 적고 사용자에게 알린다.

### 1.4 커밋 메시지 규칙

커밋 메시지와 커밋 단위 규칙은 AGENTS.md 8절이 원본이다. 각 작업 항목의 "커밋 메시지 예시" 는 그 형식(`{작업 ID} {한 일}`, 한국어 한 줄)을 따른다.

### 1.5 문서와 코드가 충돌할 때

1. 코드 작성을 멈춘다. 문서에 없는 데이터 형식, 공식, 함수, id, 문구를 코드에서 먼저 만들지 않는다.
2. 어느 문서가 원본인지 확인한다. 계산 공식과 반올림은 docs/03_계산규칙.md, 데이터 형식과 함수와 id 는 docs/02_설계문서.md, 시각 규칙과 문구 톤은 docs/04_디자인가이드.md, 기능 범위와 수용 기준은 docs/01_요구사항.md 가 원본이다.
3. 원본 문서의 수정안을 만들고 사용자에게 알린다. 확정 규칙(사용자가 정한 데이터 구조와 계산 규칙)을 바꾸는 수정은 사용자 승인 전에 반영하지 않는다.
4. 승인되면 문서를 먼저 고치고(최종 수정 날짜 갱신), 그다음 코드를 고친다. 문서 수정과 코드 수정은 같은 작업 커밋에 넣어도 된다.
5. 문서끼리 서로 다르면 3.1 표에 M 항목을 추가하고(상태 "미해결") 사용자에게 알린다.

### 1.6 단계 끝에서 멈추기

단계 끝에서 멈추는 규칙과 보고 형식은 AGENTS.md 10절이 원본이다. 이 문서에서 정하는 것은 단계별 마지막 작업 ID 뿐이다: 1단계 T1-07, 2단계 T2-05, 3단계 T3-02, 4단계 T4-17, 5단계 T5-03(T5-03 은 사용자 승인 시에만 수행하는 제안이며, 승인되지 않으면 5단계 마지막 작업은 T5-02 다. 3절 M-26).

### 1.7 결정 항목 ID 를 쓸 때

01, 02, 03, 04 문서가 각자 D-01 부터 번호를 매기므로 같은 ID 가 문서마다 다른 뜻이다. 결정 항목을 가리킬 때는 문서 번호를 앞에 붙인다. 예: "03 D-01", "02 D-12", "04 15절 1".

### 1.8 공통 금지 사항

금지 사항의 원본은 AGENTS.md 다. 작업 항목에서 자주 걸리는 것만 다시 적는다.

- 계산 모듈(portfolio.js, rebalance.js, transactions.js, storage.js)에 DOM 코드, 화면 문장, 숫자 표시 형식을 넣지 않는다. 실패는 메시지 ID 와 값만 담은 Result 로 반환한다(02 4.1). ui.js 에 계산 공식과 입력 검증 규칙을 넣지 않는다(02 2절).
- 쓰지 않는 코드와 중복 코드를 남기지 않는다. export 는 02 7절에서 "내부" 로 표시하지 않은 이름만 하고, 모듈 안에서만 쓰는 이름은 export 하지 않는다(02 2절). 02 7절의 공개 이름은 그것을 만드는 작업에서 export 하며, 사용처가 뒤 작업에서 생기는 것은 허용한다. T4-17 시점에는 사용처(다른 앱 모듈 또는 verify.mjs) 없는 export 가 0 개여야 한다.
- tests 폴더와 package.json 을 만들지 않는다. 화면 검증 스크립트는 skills/ui-verify/scripts/ 에 두고 커밋한다(2.3). 스크린샷, 내려받은 파일, 임시 데이터 파일은 저장소 밖 임시 폴더에 두고 커밋하지 않는다.
- 로컬 서버에 의존하는 기능을 만들지 않는다. 정적 서버는 확인 용도로만 쓴다.

## 2. 작업 항목 형식과 공통 검증 방법

### 2.1 작업 항목 형식

모든 작업 항목은 아래 순서의 항목을 가진다.

| 항목 | 내용 |
|---|---|
| 제목 | `### {작업 ID} {작업명}` |
| 목적 | 이 작업으로 무엇이 가능해지는지 한두 문장 |
| 대상 파일 | 만들거나 고치는 파일 |
| 참고 문서 | 문서와 절 번호. 원본 정의가 있는 곳 |
| 작업 내용 | 번호 목록의 구체적 단계 |
| 완료 기준 | "- [ ]" 체크 목록. 완료된 작업은 "- [x]" |
| 검증 방법 | 실행할 명령과 화면 확인 시나리오 |
| 커밋 메시지 예시 | AGENTS.md 8절 형식의 한 줄 |

작업 항목의 제목 `### {작업 ID} {작업명}`(예: `### T1-01 요구사항 정의서 작성`, `### E-01 자산 비중 원형 차트`)은 docs 공통 형식의 하위 제목 번호 규칙("### 1.1 ...")의 예외로 허용한다. 4절~9절에만 적용한다.

### 2.2 계산 검증 (calc-rule-verify)

- 실행 위치는 프로젝트 루트다. Node 22 이상이 필요하다.
- 전체 실행: `node skills/calc-rule-verify/scripts/verify.mjs`
- 사례 지정: `node skills/calc-rule-verify/scripts/verify.mjs C-01 R-03` 또는 묶음 지정 `node skills/calc-rule-verify/scripts/verify.mjs C`
- 구현 중간 단계: `--allow-missing` 을 붙이면 아직 없는 모듈이나 함수를 쓰는 검사를 SKIP 으로 표시하고 실패로 세지 않는다. T4-05 이후에는 이 옵션 없이 실행한다.
- 종료 코드: 모든 검사가 PASS 면 0, FAIL 이 하나라도 있거나 `--allow-missing` 없이 SKIP 이 있으면 1 이다.
- 세부 동작은 T2-04 와 skills/calc-rule-verify/SKILL.md 를 따른다.

### 2.3 화면 검증 (ui-verify)

화면 기능은 프로젝트 스킬 skills/ui-verify 의 스크립트 `skills/ui-verify/scripts/verify_ui.py`(Python Playwright, webapp-testing 방식)로 확인한다. 스크립트와 SKILL.md 는 T2-05 에서 만든다. webapp-testing 스킬이 설치되어 있지 않아도 같은 방식으로 한다.

준비(한 번만):

```
py -m pip install playwright
py -m playwright install chromium
```

- `py` 는 Windows 의 Python 런처다(이 저장소 작업 PC 는 Python 3.14). py 가 없는 환경은 `python3` 으로 바꿔 쓴다.

실행(프로젝트 루트에서):

```
py skills/ui-verify/scripts/verify_ui.py T4-07
py skills/ui-verify/scripts/verify_ui.py
py skills/ui-verify/scripts/verify_ui.py --list
py skills/ui-verify/scripts/verify_ui.py --base-url https://{사용자 이름}.github.io/{저장소 이름}/
```

1. 인자로 작업 ID 를 주면 그 작업의 시나리오만, 인자가 없으면 등록된 모든 시나리오를 실행한다. `--list` 는 등록된 시나리오 목록만 출력한다.
2. `--base-url` 이 없으면 스크립트가 프로젝트 루트에서 `py -m http.server 8000 --bind 127.0.0.1` 과 같은 정적 서버(Python 표준 라이브러리 http.server)를 확인 용도로만 띄우고 끝나면 종료한다. 브라우저 주소는 `http://localhost:8000/` 이다. 허용 주소와 이유는 01 6.2 를 따른다. 손으로 화면을 볼 때도 같은 명령으로 서버를 띄운다.
3. 각 화면 작업(T3-01 이후)은 그 작업 항목의 "검증 방법" 시나리오를 작업 ID 이름으로 verify_ui.py 에 추가하고 실행한다. 이전 작업의 시나리오는 지우지 않고 함께 다시 실행해 회귀를 확인한다. 화면이 바뀌어 이전 시나리오의 기대값이 달라지면 그 작업에서 문서 근거와 함께 고친다.
4. 요소는 02 9절의 id 로 찾는다. 기대 문구는 01 5절 문구(머리말은 04 13.1)를 쓴다.
5. 확인 대화상자(confirm)는 `page.on("dialog", ...)` 로 문구를 기록한 뒤 accept 또는 dismiss 한다.
6. 미리 데이터를 넣어야 하는 시나리오는 `skills/ui-verify/scripts/fixtures.py` 의 사례 데이터(03 14절 사례를 02 5.5 저장 객체로 바꾼 것)를 `page.add_init_script` 로 localStorage 키 `portfolio-tracker:v1` 에 넣고 페이지를 연다.
7. 모든 시나리오 끝에 스크립트가 공통으로 확인한다:
   - 콘솔 오류(console error, pageerror)가 0 건이다.
   - 검사 대상 주소(localhost 또는 `--base-url` 의 출처) 밖으로 나가는 요청이 0 건이다(01 NFR-07).
   - 하단 `#disclaimer` 문구가 01 8절과 같다.
8. 너비 확인이 필요한 작업은 360, 768, 1280px 세 너비에서 `document.documentElement.scrollWidth <= window.innerWidth` 를 확인한다.
9. 종료 코드는 모든 시나리오가 통과하면 0, 하나라도 실패하면 1 이다. 결과는 시나리오별 통과/실패로 HANDOFF.md 에 요약한다.
10. 스크린샷과 내려받은 파일 같은 임시 산출물은 저장소 밖 임시 폴더에만 두고 커밋하지 않는다.

### 2.4 문서 검증 (doc-writing-rules)

- 머리말 형식, 목차와 본문 제목 일치, 평서문 문체, 용어 통일을 doc-writing-rules 스킬의 점검 목록으로 확인한다.
- 이모지와 장식 기호 검사: `grep -nP "[^\x00-\x7F\x{AC00}-\x{D7A3}\x{3131}-\x{318E}]" {파일}` 의 출력이 없어야 한다. 출력된 문자는 하나씩 확인해 ASCII 나 한글로 바꾼다.

### 2.5 코드 구조 점검

- 계산 모듈 DOM 접근 검사: `grep -nE "document|window|localStorage|innerHTML" js/portfolio.js js/rebalance.js js/transactions.js` 의 출력이 없어야 한다. storage.js 는 localStorage 만 허용한다.
- import 관계 검사: `grep -n "^import" js/*.js` 의 결과가 02 3절 표와 같아야 한다.
- 미사용 export 검사: 각 `export` 이름을 `grep -rn "{이름}" js skills` 로 찾아 정의 외 사용처가 있는지 확인한다.

## 3. 결정 기록

T1-07 에서 01~04 문서 간 불일치(M 항목)와 문서별 결정 항목(D 항목)을 모두 확정했다. 2026-10-21 사용자가 "결정 필요 항목은 전부 추천안대로 진행" 으로 일괄 승인했고, 문서마다 권장안이 다를 때는 3.1 M 항목의 권장안을 따랐다. 결정 내용의 원본은 각 행의 "원본" 위치이며 이 절은 기록이다. 구현할 때는 원본 문서를 읽는다.

이후 문서끼리 다른 내용이나 사용자 확인이 필요한 해석이 새로 생기면 3.1 에 다음 번호(현재 M-36 부터)로 항목을 추가하고 상태를 "미해결" 로 적은 뒤 사용자에게 알린다. 미해결 항목의 영향 작업은 해소 전에 시작하지 않는다(1.5).

### E-03 해외 종목 달러 입력과 환율 환산

목적: 달러로 거래한 종목을 원화로 환산해 보유 현황, 비중, 리밸런싱에 포함한다.

대상 파일: js/portfolio.js, js/transactions.js, js/storage.js, js/ui.js, js/main.js, index.html, docs/01~04, skills/calc-rule-verify/scripts/verify.mjs

참고 문서: 02 5절, 7절, 13.2, 03 3절, 4절, 6절, 7절

제안 (구현 전 사용자 승인 필요), 데이터 구조:

- 거래에 두 필드를 추가한다: `currency`("KRW" | "USD"), `fxRate`(거래 당시 원/달러 환율, 0보다 큰 수. `currency` 가 "KRW" 이면 1).
- `price` 는 그 거래 통화 단위의 1주 가격이다. `fee` 는 기존처럼 원 단위다.
- 같은 종목명은 하나의 통화만 가진다(자산군 규칙과 같은 방식으로 검사). 종목명 "현금" 은 "KRW" 만 허용한다.
- 현재가 `prices` 는 각 종목 통화 단위다. 현재 환율은 새 키 `fxRates: { "USD": number }` 에 둔다.
- 저장 객체 version 2: `{ version: 2, transactions, prices, fxRates, targets }`. localStorage 키는 `"portfolio-tracker:v2"` 로 바꾼다.

제안 (구현 전 사용자 승인 필요), 공식(평균단가와 실현손익은 원화 기준):

```
매수: A = (Q x A + q x p x fxRate + f) / (Q + q)
매도: R = R + (p x fxRate - A) x q - f
평가 현재가(원) P = 현재가 x fxRates[currency]   (currency 가 "KRW" 이면 현재가 그대로)
현재가 미입력: P = A (기존 규칙과 같음)
현재 환율 미입력(USD 종목인데 fxRates.USD 없음): P = A 로 평가하고 "환율 미입력" 표시
```

검산 예시 1건(수수료 0 매수, 수수료 있는 매도):

| 순서 | 거래 | 계산 | 보유수량 | 평균단가(원) | 실현손익(원) |
|---|---|---|---|---|---|
| 1 | USD 종목 10주 100달러 매수, fxRate 1300, 수수료 0 | (0 + 10 x 100 x 1300 + 0) / 10 | 10 | 130000 | 0 |
| 2 | 현재가 110달러, fxRates.USD 1350 으로 평가 | 평가금액 10 x 110 x 1350 = 1485000, 평가손익 1485000 - 1300000 = 185000, 수익률 185000 / 1300000 x 100 = 14.2307... | 10 | 130000 | 0 |
| 3 | 4주 120달러 매도, fxRate 1320, 수수료 1000 | (120 x 1320 - 130000) x 4 - 1000 = 28400 x 4 - 1000 | 6 | 130000 | 112600 |

표시값: 2번 수익률 14.23.

제안 (구현 전 사용자 승인 필요), version 1 -> 2 이전 방법:

1. 앱 시작 시 `"portfolio-tracker:v2"` 키가 있으면 그것을 쓴다.
2. 없고 `"portfolio-tracker:v1"` 키가 있으면 기존 version 1 검증(02 5.7)을 통과한 경우에만 변환한다: 모든 거래에 `currency: "KRW"`, `fxRate: 1` 을 붙이고, `fxRates: {}` 를 추가하고, `version: 2` 로 바꾼다.
3. 변환 결과를 version 2 검증으로 다시 확인한 뒤 `"portfolio-tracker:v2"` 에 저장한다. `"portfolio-tracker:v1"` 값은 지우지 않고 백업으로 남긴다.
4. v1 값이 검증에 실패하면 변환하지 않고 기존 손상 데이터 처리(01 4.11 기준 4)를 따른다.
5. JSON 불러오기는 version 1 과 2 를 받는다. version 1 파일은 같은 방식으로 변환한 뒤 확인 창을 띄운다. 내보내기는 항상 version 2 다.

### E-04 CSV 로 거래내역 일괄 등록

참고 문서: 02 5.1, 5.2, 7.2, 13.3, 01 6절 NFR-03, NFR-09

제안 (구현 전 사용자 승인 필요), CSV 열 형식:

- 문자 인코딩 UTF-8(BOM 있어도 허용), 구분자 쉼표, 줄 끝 LF 또는 CRLF, 큰따옴표 묶기와 `""` 이스케이프는 RFC 4180 을 따른다.
- 첫 줄은 머리 줄이며 정확히 `date,name,assetClass,type,quantity,price,fee` 이다. 순서가 다르거나 열이 더 있으면 파일 전체 오류다.
- 값은 저장 형식 그대로다: date 는 YYYY-MM-DD, assetClass 는 stock/bond/cash/other, type 은 buy/sell. fee 빈칸은 0. 한글 표시명(주식, 매수 등)은 받지 않는다.
- 빈 줄은 건너뛴다. 데이터 줄은 최대 5,000 줄이다.
- 예:

```
date,name,assetClass,type,quantity,price,fee
2026-01-02,종목S,stock,buy,100,60000,0
2026-01-02,현금,cash,buy,1000000,1,
"2026-01-03","종목, 쉼표 포함",other,buy,5,10000,0
```

제안 (구현 전 사용자 승인 필요), 처리와 오류:

1. js/csv.js 의 `parseCsv(text: string) -> Result<TransactionInput[]>` 가 CSV 를 02 5.2 `TransactionInput` 배열로 바꾼다. DOM 을 쓰지 않는 순수 모듈이다. import 없음.

### E-05 적립식 투자 시뮬레이터

목적: 월 투자금, 기간, 예상 수익률로 적립식 투자의 예상 결과를 계산하고 그래프로 보여준다.

대상 파일: js/simulator.js(제안), js/charts.js(제안), js/main.js, js/ui.js, index.html, css/style.css, docs/01~04

참고 문서: 02 13.4, 이 문서 E-01

제안 (구현 전 사용자 승인 필요), 입력:

| 입력 | 단위 | 조건 |
|---|---|---|
| 월 투자금 M | 원 | 1 이상의 정수 |
| 기간 Y | 년 | 1 이상 50 이하의 정수. 개월 수 n = 12 x Y |
| 예상 연 수익률 a | % | -99.9 이상 100 이하, 소수 첫째 자리까지 |

제안 (구현 전 사용자 승인 필요), 월 복리 공식:

```
월 이율 i = a / 100 / 12
매월 초에 M 을 넣고 그 달 말에 이자를 붙인다.
B_0 = 0
B_m = (B_(m-1) + M) x (1 + i)        (m = 1, 2, ..., n)
원금 S_m = M x m
수익 G_m = B_m - S_m
검산용 닫힌 식(i 가 0 이 아닐 때): B_n = M x ((1 + i)^n - 1) / i x (1 + i)
i = 0 이면 B_n = M x n
```

- 연 수익률을 12로 나누는 명목 방식이다. 연 실효 수익률 기준((1 + a/100)^(1/12) - 1)과 결과가 다르므로 승인 시 둘 중 하나를 정한다.
- 내부 계산은 반올림하지 않고 표시만 원 단위로 반올림한다(03 13절과 같은 원칙).

검산된 예시: M = 1,000,000, Y = 1(n = 12), a = 12 -> i = 0.01

| m | B_m (내부값) | 표시 |
|---|---|---|
| 1 | 1010000 | 1,010,000 |
| 2 | 2030100 | 2,030,100 |
| 12 | 12809328.0433... | 12,809,328 |

- 닫힌 식: 1,000,000 x (1.01^12 - 1) / 0.01 x 1.01 = 1,000,000 x 12.6825030... x 1.01 = 12,809,328.04... (1.01^12 = 1.1268250301...)
- 원금 S_12 = 12,000,000, 수익 G_12 = 809,328(표시).
- 점화식과 닫힌 식의 결과 차이가 0.000001 이하임을 Node 로 확인했다.

제안 (구현 전 사용자 승인 필요), 구조와 화면:

- js/simulator.js: `simulate(input: { monthly: number, years: number, annualRate: number }) -> Result<SimRow[]>`. `SimRow = { month, principal, balance, gain }`. 순수 모듈, import 없음. 입력 문자열 해석은 `portfolio.parseNumber` 를 main.js 에서 써서 숫자로 넘긴다.
- 포트폴리오 상태와 독립이다. 입력값은 저장하지 않는다(AppData 형식을 바꾸지 않기 위해서다). 저장 여부는 승인 시 다시 정한다.
- 화면: 새 section `#simulator-section`, 입력칸 `#sim-monthly`, `#sim-years`, `#sim-rate`, 메시지 `#sim-message`, 연말 결과 표 `#sim-table`, 선 그래프 `canvas#sim-chart`(원금 S 와 평가금액 B 두 선). 그래프는 E-01 의 Chart.js 와 charts.js 를 쓴다. 계산 버튼 없이 입력이 바뀌면 다시 계산한다.
- 문구는 투자 권유로 읽히지 않게 "예상" 과 고지 문구를 유지한다.

작업 내용:

1. E-01 완료 후, 사용자 승인을 받아 01, 02, 03(공식과 검증 사례), 04(영역, 문구)를 고친다.

3. simulator.js -> 화면 -> 그래프 순서로 구현한다.

완료 기준:

- [ ] a = 0 이면 B_n = M x n 이다.
- [ ] 입력 조건 밖의 값은 오류를 보이고 계산하지 않는다.
