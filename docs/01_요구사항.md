## 1. 목적과 배경

### 1.1 목적

개인 투자자가 매수/매도 거래를 직접 기록하고, 종목별 평균단가, 수익률, 실현손익과 자산군별 비중을 확인하며, 목표 비중에 맞추려면 자산군별로 얼마를 사고팔아야 하는지 계산하는 웹 앱을 만든다.

### 1.2 배경

- 여러 계좌에 나뉜 자산을 한곳에 모아 자산군 비중을 보려면 지금은 스프레드시트를 직접 만들어야 한다. 이 앱은 정해진 입력 형식과 계산 규칙으로 그 작업을 대신한다.
- 실시간 시세, 계정, 서버를 두지 않는다. 현재가는 사용자가 직접 입력하고, 데이터는 사용자의 브라우저에만 저장한다. 그래서 정적 페이지로 GitHub Pages 에 배포할 수 있다.
- 통화는 원화 하나만 다룬다. 해외 종목과 환율은 확장 기능이다(3.2 참고).

### 1.3 MVP 완료 판단

다음을 모두 만족하면 MVP 가 완료된 것으로 본다.

1. 4절의 FR-01 부터 FR-14 까지 모든 수용 기준을 만족한다.
2. skills/calc-rule-verify/scripts/verify.mjs 가 docs/03_계산규칙.md 의 모든 검증 사례를 통과한다.
3. GitHub Pages 에 배포한 주소에서 6절의 NFR 을 만족하며 동작한다.

## 2. 대상 사용자와 사용 상황

### 2.1 대상 사용자

- 국내 주식, ETF, 채권 등 원화 자산에 직접 투자하는 개인 투자자
- 여러 증권 계좌의 거래를 한곳에 정리하려는 사람
- 웹 브라우저를 쓸 줄 알고 파일을 내려받고 선택할 수 있는 정도의 사용자. 프로그래밍 지식은 가정하지 않는다.

### 2.2 사용 상황

| 번호 | 상황 | 사용자가 하는 일 | 관련 요구사항 |
|---|---|---|---|
| U-01 | 거래 직후 기록 | 증권사 앱에서 체결한 거래를 그대로 입력한다. | FR-01, FR-04 |
| U-02 | 정기 점검(예: 월 1회) | 종목별 현재가를 갱신하고 보유 현황과 자산 비중을 확인한다. | FR-05, FR-06, FR-07 |
| U-03 | 리밸런싱 시점 | 목표 비중을 입력하고 자산군별 리밸런싱 금액을 확인한다. 실제 주문은 증권사 앱에서 한다. | FR-08, FR-09 |
| U-04 | 잘못 입력한 거래 정정 | 거래를 삭제하고 다시 입력한다. | FR-03 |
| U-05 | 백업과 기기 이동 | JSON 파일로 내보내고, 다른 브라우저나 기기에서 불러온다. | FR-11, FR-12 |

### 2.3 사용 환경 가정

- 주 사용 환경은 PC 브라우저다. 휴대폰 브라우저에서는 조회와 간단한 입력을 할 수 있어야 한다(NFR-05).
- 한 브라우저에서 한 사람이 하나의 포트폴리오를 관리한다.

| 자산 비중(자산군별 평가금액과 비중) | FR-07 |

| localStorage 자동 저장 | FR-10 |

### 3.2 확장

확장 기능은 MVP 에서 구현하지 않는다. 상세 내용은 docs/05_작업지시서.md 에 아래 ID 로 기록한다. 확장 기능에 필요한 새 데이터 형식이나 공식은 "제안 (구현 전 사용자 승인 필요)"으로 표시하고, 승인 전에는 구현하지 않는다.

| ID | 기능 | 비고 |
|---|---|---|
| E-01 | 자산 비중 원형 차트 | Chart.js(CDN, 버전 고정). MVP 에서는 Chart.js 를 로드하지 않는다. |
| E-02 | 종목별 수익률 막대 차트 | Chart.js 사용 |
| E-03 | 해외 종목 달러 입력과 환율 환산 | 데이터 구조 변경이 필요하다. |
| E-04 | CSV 로 거래내역 일괄 등록 | CSV 열 형식 정의가 필요하다. |
| E-05 | 적립식 투자 시뮬레이터 | 월 투자금, 기간, 예상 수익률 -> 복리 결과 그래프 |

### 3.3 하지 않는 것

| 항목 | 이유 |
|---|---|
| 실시간 시세 조회, 시세 API 연동 | 현재가는 사용자가 직접 입력한다. 외부 API 키와 서버가 필요해진다. |
| 로그인, 계정, 사용자 구분 | 서버가 없다. 한 브라우저에 한 포트폴리오만 둔다. |
| 서버 저장, 기기 간 자동 동기화 | 데이터는 브라우저에만 저장한다. 기기 이동은 JSON 파일로 한다. |
| 세금 계산(양도소득세, 배당소득세, 증권거래세 등) | 세법 해석이 필요하고 책임 범위를 벗어난다. 세금은 사용자가 수수료 칸에 넣을지 스스로 정한다. |
| 배당금, 이자 기록 | 거래 데이터 구조에 없는 항목이다. |
| 증권사 계좌 연동, 주문 실행 | 앱은 계산만 한다. |
| 종목 추천, 투자 의견 제시 | 계산 도구의 범위를 벗어난다. |
| 리밸런싱 주수 계산 | 결과는 자산군별 금액만 보여준다. |
| 거래 수정 | MVP 에서는 삭제 후 다시 입력한다. |
| 여러 포트폴리오 관리 | 저장 키가 하나다. |
| 액면분할, 병합, 공매도 처리 | 계산 규칙에 정의되어 있지 않다. |
| 주식 매수/매도 시 현금 잔고 자동 증감 | 거래는 서로 연결되지 않는다. 현금 변화는 사용자가 현금 거래로 따로 입력한다. |

## 4. 기능 요구사항

### 4.1 공통 사항

- 요구사항 ID 는 FR-두자리 번호다. 각 요구사항은 "내용"과 "수용 기준"을 가진다. 수용 기준은 화면에서 직접 확인할 수 있는 결과로 쓴다.
- 데이터 형식(거래, 현재가, 목표 비중, 저장 객체)은 docs/02_설계문서.md 의 데이터 구조 절을 따른다. 이 문서는 형식을 다시 정의하지 않는다.
- 계산 공식과 반올림 방법은 docs/03_계산규칙.md 를 따른다. 이 문서는 공식을 다시 쓰지 않는다.
- 거래, 현재가, 목표 비중 중 하나라도 바뀌면 보유 현황, 자산 비중, 리밸런싱 결과를 모두 다시 계산해 화면에 반영하고 저장한다. 별도의 "계산" 버튼은 두지 않는다.
- 사용자에게 보여주는 메시지 문구는 5절에 정의한 것만 쓴다.

### 4.2 FR-01 거래 입력

내용: 날짜, 종목명, 자산군, 구분(매수/매도), 수량, 가격, 수수료를 입력해 거래 1건을 추가한다.

수용 기준:
1. 모든 항목을 올바르게 입력하고 추가하면 거래 내역에 1건이 늘고, 보유 현황, 자산 비중, 리밸런싱 결과가 즉시 다시 계산된다.
2. 자산군 선택지는 주식, 채권, 현금, 기타 4개이고 각각 stock, bond, cash, other 로 저장된다. 자산군은 기본 선택값 없이 사용자가 고른다.
3. 구분 선택지는 매수, 매도이고 각각 buy, sell 로 저장된다. 기본 선택값은 매수다.
4. 수수료 칸을 비워 두면 0 으로 저장된다.
5. 종목명은 앞뒤 공백을 제거한 값으로 저장된다. 앞뒤 공백을 제거한 문자열이 완전히 같으면 같은 종목이다(대소문자, 중간 공백이 다르면 다른 종목).
6. 거래 id 는 crypto.randomUUID() 로 만든다.
7. 5절의 검증에 걸리면 거래를 추가하지 않고 해당 메시지를 보여주며, 사용자가 입력한 값은 지우지 않는다.

### 4.3 FR-02 거래 내역 표시

내용: 저장된 모든 거래를 표로 보여준다. 열은 날짜, 종목명, 자산군, 구분, 수량, 가격, 수수료, 삭제 버튼이다.

수용 기준:
1. 거래는 계산 처리 순서와 같은 순서로 표시한다. 날짜 오름차순이고, 같은 날짜는 입력 순서(저장 배열 순서)다.
2. 자산군과 구분은 화면 표시명(주식/채권/현금/기타, 매수/매도)으로 보여준다.
3. 거래가 0건이면 표 대신 빈 상태 문구 IN-01(5.5)을 보여준다.
4. 숫자 열은 FR-13 형식을 따른다.

### 4.4 FR-03 거래 삭제

내용: 거래 내역의 각 행에서 그 거래를 삭제한다. 거래 수정 기능은 MVP 에 없다.

수용 기준:
1. 삭제 버튼을 누르면 확인 대화상자에 확인 문구 C-01(5.4 참고)을 보여준다. 취소하면 아무것도 바뀌지 않는다. 확인 대화상자는 생략하지 않는다(되돌리기 기능이 없기 때문이다).
2. 확인하면 거래가 삭제되고 모든 결과가 다시 계산되며 저장된다.
3. 삭제하면 이후 매도가 보유수량을 초과하게 되는 경우 삭제하지 않고 VE-11 을 보여준다.

### 4.5 FR-04 현금 거래

내용: 현금은 종목명 "현금", 자산군 현금(cash), 수량 = 금액(원), 가격 = 1 로 입력한다. 입금은 매수, 출금은 매도로 입력한다.

수용 기준:
1. 종목명 "현금", 자산군 현금, 매수, 수량 1000000, 가격 1, 수수료 0 을 입력하면 보유 현황에 현금 보유수량 1,000,000, 평가금액 1,000,000 이 표시된다.
2. 현금 종목의 현재가는 1 로 고정되어 표시되며 입력할 수 없다.
3. 종목명이 "현금"인데 자산군이 현금이 아니거나 가격이 1 이 아니면 VE-08 을 보여주고 추가하지 않는다.
4. 주식 등 다른 종목의 매수/매도는 현금 보유수량을 바꾸지 않는다.
5. 현금 거래의 수수료 처리와 자산군 현금에 "현금" 외 종목명을 쓰는 경우의 규칙은 docs/03_계산규칙.md 12절을 따른다.

### 4.6 FR-05 현재가 입력

내용: 보유 현황의 각 종목 행에서 현재가를 직접 입력한다.

수용 기준:
1. 현재가를 입력하면 그 종목의 평가금액, 평가손익, 수익률과 자산 비중, 리밸런싱 결과가 즉시 다시 계산되고 저장된다.
2. 현재가 칸을 비우면 그 종목은 "현재가 미입력" 상태가 되고 저장된 현재가 값도 제거된다.
3. "현재가 미입력" 종목은 docs/03_계산규칙.md 의 현재가 미입력 규칙에 따라 평가하고, 행에 "현재가 미입력" 을 표시한다.
4. 0 이하이거나 숫자가 아닌 값은 저장하지 않고 VE-12 를 보여준다. 이전 값은 유지한다.

### 4.7 FR-06 보유 현황

내용: 종목별로 종목명, 자산군, 보유수량, 평균단가, 현재가, 평가금액, 평가손익, 수익률, 실현손익을 보여준다.

수용 기준:
1. docs/03_계산규칙.md 의 평균단가, 실현손익 검증 사례를 입력하면 같은 결과가 표시된다.
2. 보유수량이 0 이 된 종목도 실현손익을 확인할 수 있다. 표시 방식(같은 표에 표시, 평가 관련 칸은 `-`)은 docs/02_설계문서.md 6.2 를 따른다.
3. 평가손익, 수익률, 실현손익은 양수면 수익 색(빨강), 음수면 손실 색(파랑), 0 이면 기본 글자색이다. 색 값은 docs/04_디자인가이드.md 를 따른다.
4. 거래가 0건이면 표 대신 빈 상태 문구 IN-02(5.5)를 보여준다.
5. 행 정렬 기준은 docs/02_설계문서.md 에서 정한다.

### 4.8 FR-07 자산 비중

내용: 자산군 4개(주식, 채권, 현금, 기타)별 평가금액과 비중, 그리고 총평가금액을 보여준다.

수용 기준:
1. 보유하지 않은 자산군도 항상 표시한다. 평가금액은 0, 비중은 0.00 으로 보여준다(표 안 비중에는 % 를 붙이지 않는다. FR-13 기준 4).
2. 현재가 미입력 종목은 FR-05 수용 기준 3 의 평가금액으로 포함된다.
3. 총평가금액이 0 이면 비중을 표시하지 않고 안내 문구 IN-03(5.5)을 보여준다.
4. 반올림 때문에 표시된 비중의 합이 100.00% 가 아닐 수 있다. 이를 보정하지 않는다.

### 4.9 FR-08 목표 비중 입력

내용: 자산군 4개의 목표 비중을 퍼센트로 입력한다. 기본값은 0 이고 소수 첫째 자리까지 입력할 수 있다. 입력값의 합계를 함께 보여준다.

수용 기준:
1. 처음 실행하면 4칸 모두 0 이고 합계는 0.0% 로 표시된다.
2. 값을 바꾸면 합계가 즉시 갱신되고 목표 비중이 저장된다.
3. 저장된 목표 비중의 합계는 100 이 아니어도 된다. 합계 100 은 리밸런싱 계산의 조건이다(FR-09).
4. 33.3, 33.3, 33.4, 0 을 입력하면 합계 100 으로 판정되어 리밸런싱이 계산된다. 부동소수점 오차로 판정이 틀리면 안 된다. 판정 방법은 docs/03_계산규칙.md 에서 정한다.
5. 입력칸이 비어 있거나, 숫자가 아니거나, 범위를 벗어나면 VE-13, 소수 둘째 자리 이상이면 VE-14 를 보여주고 저장하지 않는다. 이전 저장값을 유지한다. 세부 규칙은 docs/02_설계문서.md 7.3 `parseTargetInput` 을 따른다.

### 4.10 FR-09 리밸런싱 계산

내용: 자산군별 리밸런싱 금액과 구분(매수/매도/유지)을 보여준다. 표의 열은 docs/02_설계문서.md 9.6 을 따른다(현재 비중은 자산 비중 표에 있으므로 이 표에 두지 않는다). 주수는 계산하지 않는다.

수용 기준:
1. docs/03_계산규칙.md 의 리밸런싱 검증 사례를 입력하면 같은 결과가 표시된다.
2. 리밸런싱 금액은 부호 없이 절댓값으로 표시하고, 방향은 구분 열에 매수 또는 매도로 표시한다. 부호 있는 금액(예: -1,000,000)으로 표시하지 않는다.
3. 화면 표시 기준으로 반올림한 금액이 0원이면 구분은 "유지"이고 금액은 0 으로 표시한다.
4. 목표 비중 합계가 100 이 아니면 결과 표 대신 VE-15 안내를 보여준다.
5. 총평가금액이 0 이면 결과 표 대신 VE-16 안내를 보여준다.

### 4.11 FR-10 자동 저장

내용: 거래, 현재가, 목표 비중이 바뀔 때마다 localStorage 키 "portfolio-tracker:v1" 에 저장 객체 전체를 JSON 으로 저장한다. 앱을 열면 이 키에서 불러온다.

수용 기준:
1. 거래 추가, 거래 삭제, 현재가 변경, 목표 비중 변경 각각의 직후 새로고침해도 같은 화면이 나온다.
2. 저장된 데이터가 없으면 거래 0건, 현재가 없음, 목표 비중 4개 모두 0 인 상태로 시작한다.
3. 저장에 실패하면(용량 초과, 저장소 차단 등) VE-20 을 보여준다. 화면의 데이터는 그대로 유지한다.
4. 저장된 값을 읽을 수 없거나 형식이 틀리면 VE-21 을 보여주고 빈 상태로 시작한다. 손상된 값의 처리는 docs/02_설계문서.md 5.7 을 따른다.

### 4.12 FR-11 JSON 내보내기

내용: 현재 데이터를 저장 객체와 같은 형식의 JSON 파일로 내려받는다. 파일 이름은 portfolio-tracker-YYYY-MM-DD.json 이고 날짜는 내보낸 날의 사용자 기기 기준 날짜다.

수용 기준:
1. 내려받은 파일의 내용은 같은 시점 localStorage 에 저장된 객체와 같은 구조와 값을 가진다.
2. 거래가 0건이어도 내보낼 수 있다.
3. 서버 요청 없이 브라우저 안에서 파일을 만든다.

### 4.13 FR-12 JSON 불러오기

내용: 사용자가 고른 JSON 파일의 형식을 검증하고, 확인을 받은 뒤 기존 데이터를 전부 교체한다.

수용 기준:
1. 검증을 통과하면 확인 문구 C-02 를 보여준다. 확인하면 거래, 현재가, 목표 비중이 모두 파일 내용으로 바뀌고 저장되며 화면이 다시 계산된다.
2. 확인 단계에서 취소하면 아무것도 바뀌지 않는다.
3. 검증에 실패하면 아무것도 바꾸지 않고 VE-17, VE-18, VE-19 중 해당 메시지를 보여준다.
4. 검증 범위: JSON 해석 가능 여부, version 값이 1 인지, 각 필드가 docs/02_설계문서.md 데이터 구조를 따르는지, 같은 종목이 하나의 자산군만 가지는지, 현금 규칙(FR-04)을 지키는지, 처음부터 다시 계산했을 때 보유수량을 초과하는 매도가 없는지. 목표 비중의 합계는 검증 대상이 아니다. 세부 검증 순서는 docs/02_설계문서.md 5.7, VE-18 의 {상세} 문구는 5.4 를 따른다.
5. FR-11 로 내보낸 파일을 그대로 불러오면 불러오기 전과 같은 화면이 나온다.

### 4.14 FR-13 숫자 표시 형식

내용: 화면의 모든 숫자를 일정한 형식으로 보여준다. 표시 자릿수와 반올림 방법은 docs/03_계산규칙.md 의 반올림 규칙을 따른다. 이 요구사항은 그 밖의 표시 형식을 정한다.

수용 기준:
1. 정수부에 천 단위 쉼표를 넣는다(예: 1,234,567).
2. 표의 숫자 열은 우측 정렬하고 고정폭 숫자 글꼴(font-variant-numeric: tabular-nums 등)을 쓴다.
3. 소수 자릿수가 정해진 값(평균단가, 비중, 수익률)은 자릿수를 고정해 표시한다(예: 11,000.00, 12.50). 소수점 위치를 열 안에서 맞추기 위해서다. 값 종류별 자릿수는 docs/03_계산규칙.md 13.2 를 따른다.
4. 표 안의 비중과 수익률 칸에는 % 를 붙이지 않고 열 머리에 "(%)" 를 적는다. 표 밖 문장과 목표 비중 합계 표시에는 % 를 붙인다. 단위 표기 규칙은 docs/04_디자인가이드.md 8.3 을 따른다.
5. 평가손익, 수익률, 실현손익의 양수 값에는 + 부호를, 음수 값에는 - 부호를 붙인다. 색만으로 수익과 손실을 구분하지 않기 위해서다(NFR-04).

### 4.15 FR-14 고지 문구

내용: 화면 하단에 8절의 고지 문구를 항상 표시한다.

수용 기준:
1. 문구가 8절과 글자 하나까지 같다.
2. 데이터 유무, 화면 너비와 관계없이 항상 보인다.

## 5. 입력 검증 요구사항

### 5.1 공통 규칙

- 이 절은 화면에 나오는 모든 메시지 문구(오류, 안내, 확인, 빈 상태, 도움말)의 원본이다. 다른 문서는 메시지 ID 로 이 절을 참조하고 문구를 다시 적지 않는다.
- 메시지는 앱이 직접 화면에 보여준다. 브라우저 기본 검증 말풍선 문구에 의존하지 않는다. 화면 확인 자동화에서 같은 문구를 확인할 수 있어야 하기 때문이다.
- 화면 문구의 문체와 머리말("오류: ", "안내: ") 규칙의 원본은 docs/04_디자인가이드.md 13.1 이다. 이 절의 표는 머리말을 뺀 본문만 적는다. 단, index.html 에 정적으로 두는 문구(5.5)는 화면에 나오는 글자 그대로 적는다.
- 계산과 검증 모듈은 문장을 만들지 않고 메시지 ID 와 치환 값(params)만 반환한다. 화면 모듈(js/ui.js)이 이 절의 문구 표를 코드 상수로 가지고 값을 표시 형식으로 바꿔 문장을 만든다. 반환 형식과 메시지 ID 별 반환 위치는 docs/02_설계문서.md 4.1, 11절을 따른다.
- 거래 입력에서 오류가 여러 개면 검사 순서상 첫 번째 오류 하나만 보여준다. 검사 순서: 거래 한 건의 항목 검사(VE-23, VE-26, VE-01, VE-02, VE-03, VE-22, VE-04, VE-05, VE-06, 현금 규칙 VE-08 순서) -> 자산군 일치 검사(VE-07) -> 전체 거래를 처음부터 다시 계산하는 초과 매도 검사(VE-09, VE-10). 단계 구분의 근거는 docs/03_계산규칙.md 9.3 이다. 아래 표의 행 순서는 검사 순서가 아니다.
- 오류가 나면 데이터는 바뀌지 않는다. 다음에 올바른 입력이 성공하면 이전 오류 메시지는 사라진다.
- 치환 자리 `{이름}` 은 실제 값으로 바꿔 넣는다. {자산군}은 화면 표시명(주식/채권/현금/기타), {구분}은 매수/매도, {날짜}는 YYYY-MM-DD 형식이다. 숫자({보유수량}, {매도수량}, {수량}, {합계} 등)는 docs/04_디자인가이드.md 8절 표시 형식(천 단위 쉼표 등)으로 넣는다. {상세}, {원인}은 다른 메시지 ID 의 문구를 넣는 자리다.

### 6.1 데이터 보존 한계

사용자에게 알려야 하는 한계다. README 사용법에도 같은 취지를 안내한다.

1. 데이터는 그 브라우저, 그 기기에만 있다. 다른 브라우저나 기기에서는 보이지 않는다.
2. 브라우저의 사이트 데이터 삭제, 시크릿(사생활 보호) 창 종료 시 데이터가 사라진다.
3. Safari 는 일정 기간(7일) 사용하지 않은 사이트의 저장 데이터를 지울 수 있다.
4. GitHub Pages 의 같은 사용자 주소(사용자이름.github.io) 아래 다른 프로젝트 페이지와 localStorage 출처를 공유한다. 그래서 저장 키에 "portfolio-tracker:" 접두어를 쓴다.
5. 위 이유로 사용자는 JSON 내보내기로 주기적으로 백업해야 한다. 앱은 이를 강제하지 않는다.

### 6.2 로컬 확인 환경

ES 모듈은 file:// 로 열리지 않으므로 로컬 확인에는 정적 파일 서버(예: python -m http.server)를 확인 용도로만 쓴다. crypto.randomUUID 는 보안 컨텍스트에서만 동작하므로 http://localhost 또는 http://127.0.0.1 주소로 연다. 같은 네트워크의 다른 IP 주소로 열면 동작하지 않을 수 있다.
